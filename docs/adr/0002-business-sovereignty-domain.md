# 业务流按订单类型分域主权

销售订单按渠道分为两类，业务流主权分别归属不同系统：

- **C 端订单（电商/三方仓履约）**：聚水潭为主权所有者。本系统仅承担销售合同的审批，审批通过后通过 `push-order` 推送给聚水潭，后续库存占用、生产、发货、对账由聚水潭管控；本系统只读同步发货单和库存快照。
- **B 端订单（线下大客户/经销商）**：本系统为主权所有者。完整管理三道检查（客户/信用/底价）、MRP、生产工单、库存占用、出库单、开票、收款核销。**不**回写聚水潭。

两类订单的库存分池管理，互不可见。两侧定期对账（建议每日凌晨）确保物理库存一致。

做这个决定的原因：聚水潭擅长 C 端电商履约（接入电商平台、三方仓、面单生成），但缺少 B 端制造业务需要的能力（信用额度、底价审批、MRP 净需求计算、内部审批联动）。直接在聚水潭强加这些能力代价过大，而把所有业务流迁回本地又会废弃聚水潭已有的电商履约能力。分域主权让两个系统各做自己擅长的事。

权衡：
- **代价**：两边库存分池意味着同一个 SKU 在物理仓库里需要按主权域分区（或者至少在系统中以"虚拟分仓"形式区隔），同步对账复杂度上升。
- **风险**：业务侧可能在两类订单边界模糊时不知道该走哪条流程（如线下大客户也下了电商订单），需要明确"渠道字段"和操作 SOP。
- **退路**：如果未来聚水潭增强了 B 端能力，可以分域回收，把 B 端订单也迁回聚水潭主权。
