## 一、项目概述

### 1.1 项目背景

Sales ERP 是一款面向销售团队的轻量级企业资源计划系统，旨在打通销售订单全生命周期管理，实现从客户管理、产品管理、订单创建、审批流转、ERP 同步到回款跟踪的端到端闭环。

系统深度集成**飞书（Feishu/Lark）**审批工作流和**聚水潭（Jushuitan）** ERP 数据同步，帮助销售团队减少跨系统操作，提升业务流转效率。

### 1.2 项目目标

| 目标维度 | 具体目标                                        |
| -------- | ----------------------------------------------- |
| 业务目标 | 实现销售订单线上化、审批自动化、数据同步实时化  |
| 效率目标 | 订单审批周期缩短 50% 以上，减少人工录入错误     |
| 管理目标 | 建立统一客户/产品主数据，支持多维度业务报表分析 |
| 集成目标 | 打通飞书审批和聚水潭 ERP，消除信息孤岛          |

### 1.3 目标用户

- **销售人员**：创建订单、提交审批、跟踪订单状态
- **销售主管/经理**：审批订单、查看团队业绩
- **财务人员**：核对回款、管理预付款
- **采购人员**：创建采购单、跟踪到货入库
- **系统管理员**：用户权限管理、系统配置、操作审计

### 2.2 客户管理

**功能清单：**

- 客户信息 CRUD（名称、联系人、电话、地址、等级）
- 客户等级体系：A/B/C 三级，关联不同价格策略
- 信用额度与账期管理
- **预付款余额**跟踪（支持预付款充值、消费、退款）

**关键字段：**

- `name`：客户名称
- `level`：客户等级（A/B/C）
- `creditLimit`：信用额度
- `paymentTerms`：账期（天）
- `prepaymentBalance`：预付款余额

### 2.3 产品管理

**功能清单：**

- 产品主数据 CRUD（名称、分类、描述）
- SKU 管理（规格型号、编码、价格）
- **价格体系**：基于客户等级的差异化定价
- **聚水潭 SKU 同步**：按品牌（EMIE）自动拉取 SKU 数据
- **本地图片缓存**：同步时下载远端图片到本地 `/uploads/products/`，规避图床防盗链与失效问题
- **物料分类**：树形结构多级分类（成品/半成品/原材料 → 子分类）
- **产品列表 / SKU 列表**：无限滚动懒加载 + SessionStorage 缓存，提升大数据量下的浏览体验

**关键字段：**

- `jstGoodsId`：聚水潭商品 ID
- `jstSkuId`：聚水潭 SKU ID
- `skuCode`：内部 SKU 编码
- `salePrice`：销售价
- `costPrice`：成本价
- `pic` / `localPic`：远端图片地址 / 本地缓存路径

### 2.4 销售订单（核心）

**功能清单：**

- 订单创建（草稿状态）
- 订单编辑（仅草稿/驳回/撤销状态可编辑）
- 订单提交审批（触发飞书审批实例）
- 订单状态跟踪
- 手动推送聚水潭
- **回款登记**（支持现金回款 + 预付款抵扣）
- 订单详情查看（关联审批记录、发货单）
- **数据导出**（Excel 格式）

**订单类型：**

- `sales`：普通销售订单
- `overseas`：海外提货单

**订单状态机：**

```
                    ┌────────────────────────────────────────┐
                    │                                        │
                    ▼                                        │
┌──────┐    ┌──────────────┐    ┌─────────┐    ┌──────────┐ │
│ draft │──▶│pending_approval│──▶│ approved │──▶│synced_jst│ │
└──────┘    └──────────────┘    └─────────┘    └──────────┘ │
    ▲              │                              │          │
    │           rejected                          │          │
    │           reverted                          │          │
    │              │                              ▼          │
    └──────────────┘                         ┌──────────┐    │
                                             │ shipped  │────┘
                                             └──────────┘
                                                  │
                                                  ▼
                                            ┌──────────┐
                                            │completed │
                                            └──────────┘
```

| 状态               | 说明         | 可执行操作       |
| ------------------ | ------------ | ---------------- |
| `draft`            | 草稿         | 编辑、提交审批   |
| `pending_approval` | 待审批       | 等待飞书审批结果 |
| `approved`         | 已审批通过   | 自动推送聚水潭   |
| `synced_jst`       | 已同步聚水潭 | 等待发货         |
| `shipped`          | 已发货       | 登记回款         |
| `completed`        | 已完成       | 全部回款到账     |
| `rejected`         | 已驳回       | 编辑后重新提交   |
| `reverted`         | 已撤销       | 编辑后重新提交   |
| `cancelled`        | 已取消       | 无               |

### 2.5 审批中心

**功能清单：**

- 审批记录列表查询
- 审批详情查看
- 手动通过/驳回审批（备用操作）
- **飞书审批回调处理**（核心）
- **审批状态轮询同步**（高频 10s，兜底机制）
- **状态变更日志**（记录每次状态流转的 from/to）

**审批类型：**

- `sales_order`：销售订单审批
- `collection`：回款审批
- `prepayment`：预付款充值审批
- `purchase_order`：采购单审批

**审批状态映射：**

| 飞书状态               | ERP 状态      | 说明       |
| ---------------------- | ------------- | ---------- |
| `PENDING`              | `pending`     | 审批中     |
| `APPROVED`             | `approved`    | 已通过     |
| `REJECTED`             | `rejected`    | 已驳回     |
| `TRANSFERRED`          | `transferred` | 已转交     |
| `CANCELLED`/`CANCELED` | `cancelled`   | 已取消     |
| `REVERTED`             | `reverted`    | 通过后撤销 |

**审批流程：**

1. 用户在系统提交订单/回款/预付款/采购单
2. 系统调用飞书 Open API 创建审批实例
3. 审批人在飞书收到审批卡片
4. 审批人通过/驳回/撤销后，飞书发送 Webhook 回调
5. 系统接收回调（或轮询检测到状态变化），更新业务状态，触发后续动作

### 2.6 财务模块

> 当前财务能力分散在 `sales`、`payments`、`prepayments`、`customers` 几个模块中，没有独立的 finance 顶层模块。本节统一梳理，并标注后续合并/扩展方向。

#### 2.6.1 财务字段总览

| 实体          | 财务字段                                                                                                                          | 说明                       |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| `Customer`    | `creditLimit`、`paymentTerms`、`prepaymentBalance`                                                                                | 信用额度、账期、预付款余额 |
| `SalesOrder`  | `totalAmount`、`discountAmount`、`payAmount`、`collectedAmount`、`prepaymentDeducted`、`collectionData`                           | 订单金额与回款进度         |
| `PrepaymentRecord` | `customerId`、`amount`、`paymentMethod`、`paymentDate`、`receiptUrl`、`status`、`approvalInstanceCode`                       | 预付款充值记录             |
| `PaymentRecord`    | `salesOrderId`、`amount`、`method`、`receivedAt`、`type(collection/prepayment)`、`prepaymentRecordId`、`attachments[]`        | 实际回款明细记录           |

**剩余应收公式：**

```
剩余应收 = payAmount − collectedAmount − prepaymentDeducted
```

#### 2.6.2 预付款管理（已上线）

- 预付款充值记录创建（默认 `pending`）
- `POST /prepayments/:id/submit` → 飞书审批
- 审批通过 → 状态 `approved` + 调增 `customer.prepaymentBalance`
- 驳回（`rejected`）后允许编辑重新提交
- 仅 `pending` 状态可删除

#### 2.6.3 回款管理（已上线，入口在销售订单）

- 仅当订单状态为 `approved/synced_jst/shipped` 时可登记回款
- 支持「现金回款 + 预付款抵扣」组合
- 校验：`prepaymentDeducted ≤ customer.prepaymentBalance`（容忍 0.01 浮点）
- 校验：`amount + prepaymentDeducted ≤ 剩余应收`
- 临时存入 `SalesOrder.collectionData`，走飞书审批
- 审批通过 → 写入 `PaymentRecord`、累加 `collectedAmount/prepaymentDeducted`、扣减客户预付款余额
- 全部到位 → 订单变 `completed`

#### 2.6.4 现状不足

| 问题                            | 说明                                                                                       |
| ------------------------------- | ------------------------------------------------------------------------------------------ |
| 没有独立 finance 模块            | 财务逻辑散落在多个业务模块中，财务人员缺少专属视图                                         |
| 缺少应收账款台账                 | 无法按客户聚合「未回款金额 / 逾期天数」                                                    |
| 账期未用于业务逻辑               | `paymentTerms` 字段存在但未驱动预警/拦截                                                   |
| 无银行账户/资金科目维度         | `PaymentRecord` 仅与订单挂钩，缺少资金账户、收支科目                                       |
| 缺少开票管理                     | 无 `Invoice` 实体、税额、开票申请流程                                                      |
| 报表维度有限                     | `reports/payment-collect` 只能看回款汇总，缺账龄表、对账单                                 |

#### 2.6.5 规划中扩展（Phase 7）

1. **新增 `finance` 顶层模块**，合并 `payments`，扩展：
   - `Invoice`（发票实体：抬头、税号、税率、状态、附件）
   - `BankAccount`（资金账户：账户名、银行、余额）
   - `CashFlow`（资金流水：账户、方向、金额、关联单据）
2. **应收账款台账**：按客户聚合剩余应收，结合 `paymentTerms` 计算逾期天数与账龄分桶（0-30/30-60/60-90/90+）
3. **开票流程**：开票申请 → 飞书审批 → 标记已开票 → 关联回款核销
4. **菜单新增「财务」分组**：预付款管理、回款明细、发票管理、应收账款、资金流水
5. **权限**：新增 `finance:view/edit`、`invoice:view/create/edit`、`cash_flow:view`
6. **报表扩展**：客户账龄表、应收对账单、资金日报

### 2.15 业财一体化闭环（规划中）

> 灵感来源：《一张订单在 ERP 里的漂流》。本节描述一张销售订单在 ERP 中从下单到回款的"七站漂流"理想路径，并列出当前实现与缺口，作为 Phase 8 的设计依据。

#### 2.15.1 七站漂流模型

```
①销售下单 → ②MRP/库存 → ③采购 → ④生产入库 → ⑤发货出库 → ⑥开票 → ⑦核销收款
   (三道检查)  (净需求计算)  (交期联动)  (自动匹配)   (货权转移)   (业务驱动凭证) (闭环)
```

| # | 站点 | 关键动作 | 当前状态 | 缺口 |
| - | ---- | -------- | -------- | ---- |
| 1 | **销售模块·三道检查** | 客户停用/地址、信用额度、价格底价 | ⚠️ 部分 | 不校验信用额度；无"产品底价"概念；客户启用状态已检查 |
| 2 | **库存与生产·MRP** | 净需求 = 订单 − 库存 − 在产 → 自动出工单 + 采购申请 | ⚠️ 部分 | 已有 BOM 拆解；不会自动触发 MRP；无"在产数量"概念 |
| 3 | **采购·交期联动** | 供应商交期变更 → 自动重算订单完工日 → 红灯预警 | ❌ 缺失 | 采购单无交期字段绑定销售订单；无延误级联预警 |
| 4 | **生产完工入库·自动匹配** | 扫码入库 → 自动匹配销售订单 → 可发货库存+ | ⚠️ 部分 | 已有加工单与 allocation；完工不会反向匹配 SalesOrder；无"可发货库存" |
| 5 | **发货出库·扫码拣货** | 出库单 → 拣货扫码 → 货权转移 → 传财务 | ⚠️ 部分 | 当前依赖聚水潭同步发货状态；无自建出库单；无扫码核对批次 |
| 6 | **财务开票·凭证自动化** | 出库 → 开票申请 → 审核 → 发票 + 应收凭证；账期提醒；逾期锁单 | ❌ 缺失 | 无发票实体、无开票申请、无应收凭证、无账期到期提醒、无逾期锁单 |
| 7 | **收款核销·资金闭环** | 收款单 → 勾选发票核销 → 收款凭证（借银行/贷应收） | ⚠️ 部分 | 已有 `PaymentRecord`；无"发票核销"动作；无银行账户实体；无会计凭证 |

#### 2.15.2 业财风险点

| 风险 | 当前 ERP 是否会发生 |
| ---- | ------------------- |
| 基础数据不完善（客户地址/信用/产品底价） | ⚠️ 字段存在但不强制校验 |
| 信用检查形同虚设 | ❗ 会发生 — `creditLimit` 没有任何校验 |
| 业财割裂 | ❗ 会发生 — 没有发票模块 |
| 库存管理混乱（账实不符） | ⚠️ 依赖聚水潭，本地无库存调整流水 |
| 流程执行不严格（线下办事） | ✅ 操作日志能补部分追溯 |
| 逾期与锁单失效 | ❗ 会发生 — 无锁单机制 |

#### 2.15.3 三项黄金法则

1. **所有业务动作必须在系统里进行**，杜绝"影子业务"。
2. **异常情况必须走系统工单**，确保所有变动可追溯。
3. **每个岗位站在订单全局看问题**：销售知采购交期，采购知生产进度，库房知财务信用。

#### 2.15.4 改造方向（详见 Phase 8）

1. 销售下单时启用「三道检查」：信用拦截 + 底价审批 + 客户状态校验
2. 销售订单 → MRP 联动（自动生成生产工单 + 采购申请）
3. 采购交期 ↔ 销售完工日 联动 + 延误预警（红灯机制）
4. 引入「可发货库存」（总库存 − 占用 = 可发货）
5. 自建「出库单」实体（不再完全依赖聚水潭同步）
6. 发票模块（Invoice）+ 开票申请 + 应收凭证 + 账期提醒 + 逾期锁单
7. 收款核销（收款单 ↔ 发票）+ 自动生成会计凭证
8. 「订单全链路跟踪面板」：合同 → 出库 → 发票 → 回款的所有节点状态/时间

### 4.2 关键实体说明

**SalesOrder（销售订单）**

- 状态字段 `status` 是核心，驱动整个业务流程
- `signerId` 签单人决定订单推送聚水潭时的店铺 ID
- `collectionData` 临时存储待审批的回款数据

**PurchaseOrder（采购单）**

- 关联供应商和采购明细项
- 支持到货入库（partial_received → received）
- 同样走飞书审批流程

**ApprovalRecord（审批记录）**

- 关联销售订单、预付款记录、回款记录或采购单
- `feishuInstanceCode` 飞书审批实例唯一标识
- `type` 区分订单审批/回款审批/预付款审批/采购单审批
- `status` 支持：pending/approved/rejected/transferred/cancelled/reverted

**BomHeader（BOM 物料清单）**

- 按产品 + SKU + 版本唯一标识
- 支持多版本管理，仅激活版本用于业务
- 明细项 `BomItem` 包含 `materialCategoryId/materialCategoryName`，用于跨 BOM 聚合需求

**ProductSku（SKU）**

- `jstSkuId` 关联聚水潭 SKU
- `salePrice` / `costPrice` 支持价格管理
- `propertiesValue` 存储规格属性
- `pic` 远端图片地址，`localPic` 本地缓存路径（同步时下载）

**MaterialCategory（物料分类）**

- 树形结构，支持多级分类
- `parentId` 指向父分类，`level` 表示层级深度

**ProductionOrderItemAllocation（加工单物料分配）**

- 连接 `ProductionOrderItem` 与 `PurchaseOrderItem`
- `qty` 记录从该批采购到货中投入加工的数量
- 用于实际投料溯源、成本核算与采购到货核销

## 八、关键约束与依赖

### 8.1 飞书集成约束

- **审批创建必须使用 `user_id`**（员工编号），不能使用 `open_id` 或 `union_id`
- 用户必须配置 `feishuUserId`，否则无法提交审批
- 飞书审批定义码（`approvalDefCode`）目前为硬编码，后端不做多租户隔离
- 飞书审批通过后撤销（REVERTED）的场景：飞书 API 返回 `status=APPROVED` + `reverted=true`，系统需识别并映射为 `reverted` 状态

### 8.2 聚水潭集成约束

- **签单人必须配置 `jushuitanShopId`**，否则无法推送订单
- 每个签单人可以对应不同店铺，支持多店铺业务场景
- SKU 同步按品牌 `EMIE` 过滤

### 8.3 数据一致性约束

- 订单编辑仅限 `draft`、`rejected`、`reverted` 状态
- 回款金额不能超过剩余应收款（容忍 0.01 元浮点误差）
- 预付款抵扣不能超过客户预付款余额
- 采购单到货数量不能超过采购数量

### 12.7 回滚预案

> **黄金原则**：**先回数据库，再回代码**。Bull 队列里有未处理任务时先暂停消费再回滚。

```bash
# A. 代码回滚（git 层）
git revert <commit_sha>          # 推荐：保留历史
# 或紧急：
git reset --hard <last_good_sha> # 危险，仅紧急情况

# B. 数据库回滚（按迁移数量）
docker exec -it sales-erp-app npm run typeorm:revert  # 回退一次
# 多次：循环执行

# C. 完整还原（最严重情况）
gunzip -c /tmp/backup_xxx.sql.gz | docker exec -i sales-erp-postgres \
  psql -U sales_erp -d sales_erp

# D. 暂停队列
docker exec -it sales-erp-redis redis-cli FLUSHDB  # 慎用！清空 Bull
```

**Bull 队列处理**：

- 发版前：`docker exec -it sales-erp-app node scripts/pause-jobs.js`（暂停 `jushuitan-sync`、`approval-poll`）
- 发版后：`node scripts/resume-jobs.js`
